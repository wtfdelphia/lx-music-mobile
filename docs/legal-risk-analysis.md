# fork 构建发布的法律风险分析

分析日期：2026-09-22。背景：fork `wtfdelphia/lx-music-mobile` 已完成
`fork-update-channel` 变更，基于上游 `lyswhut/lx-music-mobile` v1.9.1
建立了自有发布流水线，首个自有版本 v1.9.1.1 已发布。上游许可证为
Apache 2.0。

本文回答一个问题：这套「fork、构建、发布、分发」的做法涉及哪些法律
风险。结论先行：开源许可层面可以做到合规，有两处欠账要补；最大的敞口
在音乐版权内容与上游品牌归属，这两项由项目本身的性质决定，与是否
fork 无关。本文不构成法律意见，重要决策建议咨询执业律师。

2026-10-12 补入「本地曲库功能的净室风险」节（见四）。

## 一、开源许可（Apache 2.0）

fork、修改、再发布都是 Apache 2.0 明确授权的行为。合规要求逐项核对：

| 要求 | 现状 |
|---|---|
| 保留 LICENSE | 已保留 |
| 保留原作者版权声明 | `package.json` 的 `author` 只剩 `wtfdelphia`，原作者 lyswhut 没有保留在任何位置 |
| 修改文件有标注 | CHANGELOG 记录 fork 变更区段，可算替代 |
| 衍生作品显著注明修改过原作品（第 4 条） | README 写明「基于上游」，算满足 |

要补的两项：

- 仓库根加 `NOTICE` 文件（Apache 2.0 的标准做法），写明本产品基于
  `lyswhut/lx-music-mobile`（Apache 2.0）并给上游仓库链接
- `package.json` 的 author 恢复原作者署名，或以 contributors 字段
  体现

上游 README 第八节的「非商业、不接受商业合作及捐赠」是上游的自我约束
声明，对 fork 没有法律约束力（Apache 2.0 不允许附加限制），但遵守它是
维持上游关系、避免被针对性投诉的实际手段。

## 二、商标与品牌

Apache 2.0 第 6 条不授予商标权。「洛雪音乐」「LX Music」是上游作者的
品牌。fork 有三处混淆点：

1. 仓库名 `wtfdelphia/lx-music-mobile` 沿用项目名
2. 应用名仍是 `lx-music-mobile`（`package.json` 的 `name`），
   applicationId `cn.toside.music.mobile` 与上游相同
3. README 保留大量上游文案

用户可能把 fork 当成官方版或授权版。上游作者可以据此向 GitHub 发起
商标投诉，仓库与 Release 可能被下架。当前实际状态：上游 README 有
「谨防假冒」专段，作者对第三方修改版的一贯态度是发声明不追诉，短期
风险低；风险随发布渠道的可见度上升，不是线性关系。

低成本的缓解：README 显著声明「本仓库是第三方 fork，与上游无官方
关系、未获上游授权」，下载入口与更新日志的表述同时改掉「原始发布
地址」一类暗示官方身份的措辞。

## 三、音乐版权

这是项目本身的最大敞口，由 fork 继承，不是由本次工程改动引入。

1. 2023 年 10 月，上游因腾讯投诉移除全部内置源（`publish/version.json`
   1.2.0 条目有记录）。fork 保留着 kw、kg、tx、wy、mg 模块与自定义源
   框架，继承了同样的敞口
2. `test/scripts-regression/candidates/` 随公开仓库分发第三方脚本，
   其中包含「长青SVIP音源(二改修复版)」这类绕过付费会员的脚本。
   分发此类脚本，原作者与传播者可能触及《刑法》第 285 条（破坏计算机
   信息系统罪）或著作权刑事追诉，近年有实际判例。这些文件虽标注为
   测试候选、第三方原文，但随公开仓库分发这一事实本身构成公开传播

## 四、本地曲库功能的净室风险（GPLv3 上游）

`add-ios-local-library` 变更的功能范围参照了 `wesley666/LynMusic`
的公开描述，实现方式采用净室设计。这里单独记录这项功能特有的敞口。

事实：

1. 上游许可证是 GPL-3.0-or-later，且 README 自述包含 GPL-2.0 双许可
   的 DLNA/UPnP 组件
2. 本设计的功能范围参照了上游公开描述（README 与截图），设计者为
   可行性评估读过上游源码，净室已受污染（`design.md` §0.5 自曝）
3. 本仓库发布定位为 Apache-2.0

敞口：实现若被认定为上游的衍生作品，GPLv3 的 copyleft 会要求整个
应用按 GPL 发布，直接冲击本仓库的许可证定位。净室纪律在这里不是
姿态问题，是许可证问题。

缓解措施（已写入 `design.md` §0.5）：

- 实现者不打开、检索或复制上游源码、资源与字符串；PR 声明
- 开工硬门禁：实现前复核设计稿与规格。优先请未接触源码的人复核；
  找不到时降级为结构化自审（逐节列公开文档依据清单）并在 PR 声明
- 处置规则：疑似照搬的节按公开文档重写；无法自证依据的砍功能
- 定位符、表结构、元数据映射均为本设计新定义；图标与样式只用
  LX 现有资源

残余敞口：范围参照本身（「做什么」参照了上游功能清单）不构成代码
层面的衍生，但功能组合的相似度仍可能成为主张衍生作品时的论据之一。
缓解手段是把基线外的功能（Subsonic 通用协议、Jellyfin/Emby、文本
导入、离线下载、下载自动关联）作为 LX 自有需求独立立项，这些功能
不受净室参照约束。

2026-10-14 状态变更：项目负责人决定放弃净室定位，实现者为分析本地
曲库管理逻辑阅读了上游公开源码（分析仅用于理解与对照，不用于直接
移植）。自该日起「未参考源码」的声明失效，本功能的许可证敞口从
「被认定衍生作品才触发」上升为「存在实际接触证据，认定门槛降低」。
应对选项不变：仅自用、停止公开分发该功能、或整体重估发布许可证。
记录见 `design.md` §0.6。

## 五、平台规则

| 平台 | 风险 |
|---|---|
| GitHub | 上游或版权方发起 DMCA 或商标投诉，仓库被删。最现实、最容易发生的场景 |
| GitHub Actions | 用其构建分发规避版权技术措施的内容，违反 GitHub 服务条款，可能封号 |
| iOS 自签 | 未签名 IPA 分发已被 `ios-distribution` 规范自我限定为三条合规通道（源码自编译、TestFlight 内部测试、自签），这一项做得最稳 |

## 六、fork 相对上游的位置

| 项 | 性质 |
|---|---|
| 独立发布渠道（GitHub Release + 应用内更新推送） | 新增。「分发」行为比上游更活跃、留痕更多 |
| 音乐源与脚本的版权敞口 | 继承 |
| 新的侵权内容 | 未引入 |

## 七、建议动作

| 优先级 | 事项 | 成本 |
|---|---|---|
| 高 | 加 `NOTICE` 文件，README 显著声明第三方 fork 身份 | 低 |
| 高 | 决定是否继续公开分发 `candidates/` 里的 SVIP 类脚本；最保守做法是从公开仓库移除，仅本地持有 | 低 |
| 中 | 维持上游的非商业姿态：不商用、不接受捐赠、不加广告 | 零 |
| 中 | 控制发布渠道的可见度，不主动推广 | 零 |
| 低 | 关注上游动态：上游若收到新的平台投诉或被下架，本仓库大概率是下一批 | 零 |

## 结论

工程动作（fork、构建、发布、更新通道）在开源许可框架内是合法的，补上
`NOTICE` 与第三方声明即站得住。项目承载的内容（第三方音源、SVIP
脚本）与版权方天然对立，这部分风险由「做不做这个产品」的决策决定，
工程手段消不掉。仅自用、小规模分享，实际风险很低；公开运营，要做好
仓库随时被下架的准备。
